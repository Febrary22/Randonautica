# 일탈 (Escapade) — 게임 기획 문서 v0.1

> 란더노티카(Randonautica)에서 영감을 받되, "무작위"가 아니라 "과학적으로 필터링된 미스터리"를 지향하는
> 위치 기반 탐험 앱. 캐시워크·손목닥터9988·피크민 블룸처럼 백그라운드에서 걸음/경로를 추적하고,
> 어둡고 축축한 미지의 세계로 유저를 안내하되 절대 위험에 빠뜨리지 않는 것이 핵심 원칙이다.

이 문서는 대화에서 나온 아이디어를 구조화하고, 질문했던 부분(지도, 안전 필터링, 밀도 분석,
수익모델, GPS 스푸핑)에 대한 리서치 기반 답변과, 놓친 부분에 대한 제안을 담는다. 확정안이 아니라
**대화를 이어가기 위한 기준점**이다.

---

## 1. 지도: Google Maps를 써도 될까?

**결론: "화면에 그리는 지도"와 "판단에 쓰는 데이터"를 분리하는 하이브리드를 추천.**

| 용도 | 추천 | 이유 |
|---|---|---|
| 실제 유저에게 보여주는 지도(다크·안개·미스터리 무드) | **Mapbox GL** 또는 **MapLibre GL(오픈소스, 무료)** | Google Maps 기본 스타일은 커스텀 다크 테마 구현이 제한적. Mapbox Studio나 MapLibre 스타일 JSON은 색상·안개 레이어·조명 효과를 원하는 만큼 커스터마이징 가능. 비용도 Google보다 유리(MapLibre는 완전 무료, 타일은 OSM 기반 자체 호스팅 가능). |
| 장소 정보/역지오코딩/도보 경로 검증 | **Google Places API / Directions API** (또는 대안으로 OSM Overpass API) | 국내 POI 정확도와 보행자 경로 데이터 품질이 가장 높음. 안전성 판단(뒤에서 설명)에 필요. |
| 위험 지역(수역·절벽 등) 판별용 벡터 데이터 | **OpenStreetMap 수역/지형 폴리곤 (Overpass API)** | Google은 폴리곤 형태의 수역 데이터를 직접 제공하지 않음. OSM의 `natural=water`, `waterway=riverbank`, `natural=coastline` 태그를 미리 지역별로 캐싱해두는 방식이 필요.

즉 "Google Maps만 가져다 쓰면 될까?"에 대한 답은 **아니오에 가깝다** — 지도 SDK로만 쓰기엔 비용(무료 크레딧 초과 시 사용량 과금)과 다크 무드 구현의 자유도 문제가 있고, 안전 판별에는 Google이 제공하지 않는 폴리곤 데이터가 필요하다.

## 2. 좌표 생성 & 안전 필터링 파이프라인

제안하신 몬테카를로 + KDE/DBSCAN 흐름은 방향은 좋다. 다만 **"미스터리 밀도"와 "실제 안전/혼잡도"는 서로 다른 축**이므로 분리해서 설계할 것을 제안한다.

### 2.1 전체 흐름 (제안 수정안)

```
1) Exclusion Zone 사전 구축 (오프라인 배치 작업, 지역별 캐싱)
   - 수역(강/호수/저수지/바다) 폴리곤 + 버퍼(15~30m)
   - 급경사지(경사 30도 이상, Elevation API/SRTM) + 절벽
   - 도로/철도/고속도로 중앙, 공사장, 군사시설, 사유지(입산통제구역 등)
   → 이 exclusion mask는 몬테카를로 "샘플링 단계 이전"에 적용한다.
     (샘플링 후 걸러내면 안전 후보가 부족해질 수 있음)

2) 몬테카를로 샘플링
   - 반경 R km 내 무작위 포인트 N개(2,000개) 생성
   - Exclusion mask에 걸리는 포인트는 즉시 재샘플링(reject sampling)

3) 밀도 계산 — 두 개의 독립적인 맵 유지
   a. "이야기성 밀도맵": 폐가·오래된 사당/신사·오래된 공원·하천 산책로·좁은 골목 등
      역사/문화적 텍스처가 있는 POI 밀도 (attractor/void/anomaly 분류의 원재료)
   b. "혼잡도맵": 상권 POI 밀도, 공공 인구밀도 격자데이터(통계청 등)로
      "사람이 너무 많은 곳"을 별도로 회피 대상 처리 (attractor라도 혼잡도가 높으면 감점)

4) 패턴 분류
   - Attractor: KDE 상위 percentile (예: 상위 5%)
   - Void: KDE 하위 percentile (예: 하위 5%)
   - Anomaly: 순수 저밀도가 아니라 "주변과 고립된" 지점이므로 KDE보다
     **LOF(Local Outlier Factor)** 나 k-NN distance 기반 이상치 탐지가 더 적합.
     (DBSCAN은 군집 여부만 이진 판정하므로 3단계 분류엔 KDE+LOF 조합을 추천)

5) 접근성 검증
   - Directions API(보행자 모드)로 해당 좌표까지 실제 도보 경로가 존재하는지 확인
   - 경로가 없으면 후보 탈락 또는 가장 가까운 보행 가능 지점으로 스냅

6) 최종 스코어링 = f(이야기성 점수, 혼잡도 역점수, 접근성, 안전 통과 여부)
   → 최고 점수 지점을 이번 모험의 목적지로 확정
```

### 2.2 왜 이렇게 나누나
- 순수 저밀도(Void)를 "사람이 없는 곳"으로만 정의하면 위험 지역(공사장, 인적 없는 산길)이 섞여 나올 수 있다. 안전 필터를 **1단계(사전 exclusion)** 로 완전히 분리해야 이후 어떤 분류 로직을 붙여도 안전성이 보장된다.
- Anomaly를 KDE만으로 잡으면 "그냥 밀도가 낮은 곳"과 구분이 안 된다. LOF는 "주변 이웃과 비교해 얼마나 튀는가"를 계산하므로 란더노티카가 말하는 "이상 지점"의 원래 의도에 더 가깝다.

## 3. 백그라운드 걸음수 · 경로 추적 (캐시워크/피크민 블룸 방식)

| 플랫폼 | 걸음수 | 백그라운드 위치/경로 |
|---|---|---|
| iOS | CoreMotion(`CMPedometer`) + HealthKit | Background Location(Always 권한) 또는 significant-location-change. 심사 시 "왜 항상 위치가 필요한지" 명확히 설명 필요 |
| Android | Health Connect(Google Fit 후속 표준) | Foreground Service + `ACCESS_BACKGROUND_LOCATION`(Android 10+는 별도 심사 필수) |

- 배터리 절약: 걸음수는 가속도계 기반이라 부담이 적음. 경로(폴리라인)는 "일정 거리(10~20m) 이동 시에만 포인트 기록" 방식으로 샘플링하고, 저장 전 Douglas-Peucker 알고리즘으로 단순화.
- 오프라인 대비: 신호 약한 구간(터널, 지하)에서도 마지막 좌표를 로컬에 유지하고 복귀 시 보간.

## 4. 게임 메커니즘 — 제안 정리 + 보완

이미 제시하신 4가지(안개 해제, 엔트로피 에너지, 유물 수집, 탐험 저널)는 그대로 가되, 아래를 더하는 걸 제안한다.

| 메커니즘 | 설명 | 왜 필요한가 |
|---|---|---|
| 세이프가드 모드 | 위험 신호(배터리 부족, 야간, 인적 없는 구역 장시간 체류) 감지 시 더 밝고 붐비는 경로로 자동 재유도 + SOS 버튼 | 공포/미스터리 컨셉상 "밤에 낯선 곳"으로 유도하는 게 핵심인데, 실제 사고로 이어지면 안 됨. 가장 중요한 미싱 피스 |
| 보호자 공유 링크 | 모험 시작 시 실시간 위치를 지인에게 링크로 공유(선택) | 심야 단독 탐험의 안전판 |
| 날씨/시간 연동 | 실제 날씨 API로 안개·비 오는 날 비주얼 강화, 야간엔 톤 다운 | 요청하신 "어둡고 축축한" 분위기를 실제 환경과 동기화해 몰입 강화 |
| 감각 내비게이션 | 좌표를 지도에 바로 찍어주지 않고 진동/사운드 강도로 "가까워짐"만 힌트 | 란더노티카 대비 차별화 포인트, "탐사하는 느낌" 강화 |
| 동행 모드 | 친구와 함께 모험 | 소셜 확산 + 단독 야간 이동 리스크 완화 |
| 콘텐츠 모더레이션 | 후기/사진 게시판에 AI 필터 + 신고 기능 | 미성년자 노출, 사유지 무단침입 인증샷 등 법적 리스크 |
| 온보딩 안전 교육 | 첫 실행 시 안전 수칙 고지 + "주간 모험만" 옵션 제공 | 법적 면책 및 실제 안전 |

## 7. 가상 GPS(모킹) 방지 — 완전 차단은 불가능, 다층 방어로 리스크 관리

**전제**: 루팅/탈옥 기기 + 위조 GPS 앱 조합을 100% 막는 방법은 없다. 포켓몬고도 여전히 완전 차단은 못 하고 "탐지 후 제재" 정책으로 운영한다. 대신 **다층 신호를 합산한 리스크 스코어링**으로 관리하는 것이 현실적이다.

1. **OS 레벨 신호**: Android `Location.isMock()`(API 31+)/`isFromMockProvider()`, 고정된 고도·정확도 값 패턴 감지
2. **기기 무결성 검증**: Android **Play Integrity API**, iOS **DeviceCheck/App Attest** — 루팅/탈옥·변조 기기 감지 [[4]](https://blog.anmolthedeveloper.com/how-to-detect-fake-gps-and-mock-location-in-android-apps-a-developers-security-guide)
3. **센서 퓨전 교차검증**: 가속도계 기반 걸음수와 GPS 이동거리가 상식적으로 맞는지 대조(걸음수 0인데 GPS만 수 km 순간이동 → 의심)
4. **이상치 탐지**: 비현실적 속도/가속, IP 기반 위치와 GPS 위치의 큰 괴리, 타임존/언어 설정 불일치
5. **서버사이드 리스크 스코어링**: 위 신호를 합산해 점수화 → 의심 계정은 포인트 적립만 보류(탐험 자체는 막지 않음), 반복 시 계정 제재
6. **적용 범위를 제한**: "탐험·사진 공유"는 관대하게 허용하되, **포인트 적립·아이템 교환·랭킹처럼 실질적 보상이 걸린 부분에만** 엄격 검증 적용 — 오탐으로 선의의 유저가 피해보는 것을 최소화

## 8. 대화에서 다루지 않았지만 짚어야 할 부분

- **법적 책임/약관**: 사유지 무단 침입, 위험지역 접근에 대한 면책 고지 필요
- **미성년자 보호정책**: 심야 단독 탐험 유도 금지, 연령 확인/보호자 동의 플로우
- **개인정보/위치데이터 처리방침**: 위치는 민감정보 — 개인정보보호법/GDPR 준수, 최소 보관 기간 정책
- **배터리 소모 최적화 전략**: 위에서 언급한 샘플링 외에도 OS별 백그라운드 정책(Doze, App Standby) 대응 필요
- **커뮤니티 모더레이션 정책**: 신고·차단, 부적절 콘텐츠 자동 필터
- **오프라인/저신호 지역 대응**: 지도 타일 캐싱
- **기술 스택 미정**: 네이티브(Swift/Kotlin) vs 크로스플랫폼(Flutter/React Native) — 백그라운드 위치·헬스킷 연동 특성상 크로스플랫폼이면 네이티브 모듈 작업이 상당히 필요함. 다음 논의에서 결정 필요

## 9. 제안하는 다음 단계 (MVP 로드맵)

1. **Phase 1**: 좌표 생성 파이프라인 + 안전 필터(exclusion zone) + 기본 걸음수/경로 추적 + 심플 결과 화면
2. **Phase 2**: 엔트로피 에너지, 안개 해제, 유물 수집, 탐험 저널
